# Deploying ClubSphere to Render (Neon database)

This deployment runs two Docker web services from one Blueprint:

| Service | What it does | Public URL |
| --- | --- | --- |
| `clubsphere-backend` | FastAPI/Uvicorn on port 8000; runs `alembic upgrade head` before starting | `https://clubsphere-backend.onrender.com` |
| `clubsphere-frontend` | Vite build served by Nginx; proxies `/api` and `/health` to the backend | `https://clubsphere-frontend.onrender.com` |

The browser only talks to the frontend origin, so the refresh cookie stays
same-origin and no CORS preflight is needed for normal app traffic.

## 1. Prerequisites

- A Render account connected to the GitHub repo containing this project.
- Your Neon **production** branch connection strings (pooled + unpooled).
  Get them from the Neon dashboard; do **not** commit them.
- Optional but recommended: an Azure Blob Storage connection string for durable
  uploads. Without it, uploads are written to the container filesystem and are
  lost on redeploy/restart.

## 2. Review the committed Blueprint

`render.yaml` is committed at the repo root. Before creating the Blueprint,
check these values:

- Service names (`clubsphere-backend`, `clubsphere-frontend`). If you rename
  them, Render's generated `onrender.com` hostnames change too.
- `CORS_ORIGINS` on the backend must match your frontend's real URL.
- `ALLOWED_HOSTS` includes `*.onrender.com` (matches all Render hosts) plus the
  bare backend service name for internal health checks. Add your custom domain
  here when you have one.

Secrets are **not** in `render.yaml`. Render prompts for them on first sync.

## 3. Create the Blueprint

1. Render Dashboard → **New** → **Blueprint Instance**.
2. Select the repo and branch (`main`).
3. Render parses `render.yaml` and prompts for these secrets:
   - `DATABASE_URL` — Neon **pooled** connection string (`-pooler` host).
   - `DATABASE_URL_UNPOOLED` — Neon **direct** connection string (used by Alembic).
   - `AZURE_STORAGE_CONNECTION_STRING` — leave blank for now if you have no
     storage account yet; uploads will use local disk.
   - `JWT_SECRET_KEY` is auto-generated by Render (`generateValue: true`); you
     do not need to enter it.
4. Click **Apply** and wait for both services to build.

> Render builds the backend with `backend/Dockerfile` and the frontend with
> `frontend/Dockerfile`. The frontend's Nginx config is rendered at container
> start from `frontend/nginx.conf.template` using the backend's public hostname
> supplied by the Blueprint.

## 4. Verify the deployment

```powershell
# Health checks
curl https://clubsphere-backend.onrender.com/health
curl https://clubsphere-frontend.onrender.com/health   # proxied to backend
curl https://clubsphere-frontend.onrender.com/         # SPA shell
```

The backend `/health` endpoint returns `503` when the database is unreachable,
so a `200` confirms Neon connectivity. Sign in through the UI to confirm the
`/api/v1/auth/*` proxy and refresh cookie work end to end.

## 5. Important operational notes

- **Free plan behavior:** free web services spin down after inactivity, so the
  first request after a quiet period can take several seconds. Both services
  are set to `0.5c-512mb` in the Blueprint for steadier behavior.
- **HTTPS:** Render terminates TLS at its edge and redirects HTTP → HTTPS.
  `FORCE_HTTPS=false` on the backend avoids a redirect loop from inside the
  container. HSTS is added by Nginx on the frontend.
- **Uploads:** supply a real `AZURE_STORAGE_CONNECTION_STRING` before relying on
  file uploads in production.
- **Rate limiting client IP:** `TRUSTED_PROXY_IPS` is empty, so the backend sees
  the proxy/peer address rather than the original visitor IP. Rate limits still
  apply but are shared across visitors behind the same proxy. Set it to the
  exact proxy IP(s) if you need per-visitor throttling.
- **Custom domains:** add the domain to `CORS_ORIGINS` and `ALLOWED_HOSTS` on
  the backend, and add it under `domains:` in `render.yaml`.

## 6. Local production stack (alternative)

A local/self-hosted Docker deployment is also available:

```powershell
docker compose -f docker-compose.prod.yml --env-file .env.render up -d --build
```

`.env.render` in this workspace is a generated placeholder file (gitignored)
with a fresh JWT secret. Replace the `REPLACE_ME` Neon values before using it.
It is intentionally not named `.env.production`: the backend auto-loads that
filename from the repo root, which would leak production settings into local
development and tests.
